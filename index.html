The IoT9 B2C flow supports one lock per property today. That was never a product decision — it fell out of how credentials worked on the Spintly side. This document describes what we changed, and the six places your lock onboarding flow changes to let a user add a second lock with its own independent passcode.

How to read this

This page follows the structure of your existing Lock Onboarding reference. Anything drawn or marked in amber is new or changed in this release; everything else already works the way it does today.

Section 1What changes

An accessor used to hold exactly one credential, and permissions were granted at the accessor level. A passcode is derived from a credential, so one accessor meant one passcode — and that passcode was valid on every lock the accessor could open. Add a second lock and the user's first passcode opens it too. Since your requirement is a different passcode per lock, we could not allow the second lock.

Three changes on the Spintly side remove that limit:

AreaBeforeAfter
Locks per property1Many
Credentials per accessor1Many — one per passcode
Permission granularityaccessor → doorcredential → door
Passcode scopesame passcode on every lockone passcode per lock
Acks consumedorganisation onlyorganisation, site, network, access point
Master passcode call(serial, orgId, accessorId, …)(serial, credentialId, orgId, accessorId, …)

Nothing about OAuth, the Access SDK, provisioning, firmware, fingerprint or RFID enrolment changes.

Section 2Why one lock, and what replaces it

The whole change is the layer between the accessor and the doors. Binary Veda now decides which credential goes on which lock — and therefore which passcode opens which lock.

Section 3The eight steps, revisited

Section 4Kafka acknowledgements you must consume

Resource creation in Spintly is asynchronous. The REST call returns immediately; the resource is only usable once Spintly has created it across its services and published a resource_alive message.

Today you consume the acknowledgement for the organisation only. Organisation, site and network are all created by that same API call, and you currently proceed without waiting for the site and network acks. That has to change: with more than one lock, a lock is attached to a network, and acting before the network is confirmed will fail intermittently and be very hard to reproduce.

ResourceCreated byMessageYou must
Organisationfirst propertyresource_alivemark in sync — already done
Sitesame call as organisationresource_aliveNew mark in sync
Networksame call as organisationresource_aliveNew mark in sync
Access pointevery addLockresource_aliveNew mark in sync
Accessoraccessor added to orgaccessor_readymark accessor ready

resource_alive means this resource has been created on Spintly servers and is healthy — read it as "this id is now safe to use in the next API call." accessor_ready means the accessor exists in that organisation and can receive credentials and permissions.

Envelope

{
    "messageVersion": 1,
    "messageData": {
        "requestId": "ahds-akjshak-dsbdk-skjdskd",
        "msgType": "resource_alive",
        "dataVersion": 1,
        "data": {
            "resourceId": 123,
            "resourceName": "organisations | sites | networks | gateways | access_points"
        }
    }
}

resourceName tells you which resource the id belongs to, and resourceId is that resource's id — for a lock, resourceName is access_points and resourceId is the accessPointId Spintly assigned. The same envelope carries all five resource types, so one consumer handles them all: switch on resourceName and mark the matching record in sync.

accessor_ready

The accessor acknowledgement uses the same envelope with its own data block, carrying both ids you need to act on it:

{
    "messageVersion": 1,
    "messageData": {
        "requestId": "ahds-akjshak-dsbdk-skjdskd",
        "msgType": "accessor_ready",
        "dataVersion": 1,
        "data": {
            "accessorId": 123456,
            "orgId": 123
        }
    }
}

Three rules for the consumer

  • Be idempotent. The same ack may arrive more than once. Marking a resource in sync twice must be harmless.
  • Ignore unknown msgType values rather than retrying them, so message types we add later cannot stall your consumer.
  • Never proceed on a timeout. If an ack does not arrive, surface it and stop — do not fall through to the next API call. Your existing getLock and resumeOnboarding polling loops are the right place to hold.

Section 5Flow A — adding the first lock

This is your current flow with the extra acks, and with the permission granted against a credential rather than the accessor.

Step 1 — Organisation, site and network

Create them if the user has no property yet. Wait for all three resource_alive messages before continuing. Only then is the property usable and its synced flag true.

Step 2 — Owner accessor

If the owner has no accessor in this organisation, create one:

POST /credentialManagementV3/v1/accessors

The response carries the credential that was created with the accessor:

{
  "type": "success",
  "message": {
    "credentials": [
      {
        "integratorUniqueId": "ff766cf7-4182-4327-8898-bf2b947ec658",
        "accessorId": 107968,
        "integratorId": 123,
        "credentialTypes": [
          { "type": "passcode", "credentialId": 700000001, "format": "32_bit", "status": 1 }
        ]
      }
    ]
  }
}

Action for Binary Veda

credentialTypes holds one entry per access type that was enabled when the accessor was created — store all of them, not only the passcode one. The passcode credential is the one you bind to this first lock and whose value the user is about to set. If an id is ever lost, the get-credentials API in section 7 reads them back.

Wait for accessor_ready before granting any permission.

Step 3 — Access point

Create the access point as you do today, then wait for its resource_alive. The permission call in step 4 will fail if the access point is not yet in sync.

Step 4 — Bind the credential to the lock

Instead of the accessor-level call you use today (PATCH …/accessors/{accessorId}/permissions), use the credential-level call with the credentialId from step 2:

PATCH /permissionManagementV3/v1/organisations/{orgId}/accessors/{accessorId}
      /credentials/{credentialId}/permissions

{ "accessPointsToAdd": [4567], "accessPointsToRemove": [] }

This is the call that binds that specific passcode to that specific lock.

Step 5 — Master passcode

Call the Config SDK master-passcode function, now passing the credentialId — see section 10.

Section 6Flow B — adding the second lock

This is the new capability. The organisation, site, network and accessor already exist, so the flow is shorter — but it gains one step that has no equivalent today: requesting a new credential for the accessor the user already has.

Step 1 — Create the access point

Create the lock's access point in the existing organisation and network, then wait for its resource_alive ack. Do not request a credential before it arrives.

Step 2 — Request a new passcode credential

POST /permissionManagementV3/v1/organisations/{orgId}/accessors/{accessorId}/credential/create

{ "credentialType": "passcode" }

Response:

{
  "type": "success",
  "message": {
    "orgId": 1,
    "accessorId": 501,
    "credentialType": "passcode",
    "credentialId": 700000002
  }
}

Action for Binary Veda

Store this credentialId against the lock being onboarded. It is a different credential from the one issued at accessor creation, and it will carry a different passcode.

Step 3 — Bind the new credential to the new lock

PATCH /permissionManagementV3/v1/organisations/{orgId}/accessors/{accessorId}
      /credentials/700000002/permissions

{ "accessPointsToAdd": [4568], "accessPointsToRemove": [] }

Use the new credentialId and the new accessPointId. Do not add the new credential to the first lock unless you intend the second passcode to open it too.

Step 4 — Master passcode for the second lock

Call the SDK with the new credentialId. The user sets a passcode that is completely independent of the first lock's.

Repeat steps 1–4 for every additional lock.

Section 7Other access types

A passcode is one credential type. The same credential-per-door model applies to fingerprint, card, face, QR and wallet. What differs between them is only how the credential comes into existence and where you read its id — once it exists, every type is bound to a lock with the same call from section 9.

Access typeCredential created byTypical count per user
PasscodeSpintlyone per lock — the subject of this document
FingerprintSpintlyusually one, bound to every lock
Card (RFID)Binary Veda — Spintly cannot generate oneone per physical card
Face, QR, WalletSpintlynot in the current scope

Where a credential comes from

There are three moments at which a credential is issued, and they are the only three.

  1. When the accessor is created. Access settings are created together with the accessor, and a credential is issued for every access type enabled at that moment. These come back in the create-accessor response, in the credentialTypes array — one entry per type. This is the one place credentials are handed to you unasked, so capture all of them, not only the passcode one.
  2. The first time an access type is enabled afterwards. Enabling a type through the access-settings routes creates its credential on our side. The response does not carry it — read it with the get-credentials API below. Disabling and re-enabling the same type later does not issue a new credential; the original one is reused.
  3. Whenever you ask for another one. POST …/credential/create issues an additional credential, and it works for every access type, not just passcode. This is how a user gets a second passcode — and how you would give them a second credential of any other type if you ever needed one.

Reading a user's current credentials

Because enabling an access type does not return the credential it created, you need a way to read what a user holds. This route is the read side of everything above — the source of truth, and the recovery path if a credentialId is ever lost on your side.

GET/credentialManagementV3/v1/organisations/{orgId}/accessors/{accessorId}/credential
ParameterIn
orgIdpathorganisation the accessor belongs to
accessorIdpathaccessor whose credentials are read
credentialTypequeryoptional filter, e.g. passcode. Omit for all.

Response 200

{
  "type": "success",
  "message": {
    "orgId": 123,
    "accessorId": 107968,
    "credentials": [
      { "type": "passcode",    "credentialId": 700000001, "format": "32_bit", "status": 1 },
      { "type": "passcode",    "credentialId": 700000002, "format": "32_bit", "status": 1 },
      { "type": "fingerprint", "credentialId": 44389500,  "format": "32_bit", "status": 1 },
      { "type": "card",        "credentialId": 123456,    "format": "32_bit", "status": 1 }
    ]
  }
}
  • Each entry is the same object the create-accessor response returns inside credentialTypes, so one parser handles both.
  • Do not key on type. An accessor may hold several credentials of the same type — the two passcode entries above are a user with a different passcode on each of two locks. credentialId is the unique key.
  • Returns an empty credentials array when the accessor holds none; 400 when the accessor is not a member of the organisation.

Enabling a type is not the same as granting access

Access settings decide which credential types a user may have. The permissions call decides which locks each credential opens. A user can have fingerprint enabled and still open no doors with it until the fingerprint credential is bound to an access point.

Card is supplied by you

A card credential is a number already encoded on a physical card, so Spintly cannot generate one — you provide it. Assign it either when creating the accessor, or afterwards:

PATCH/credentialManagementV3/v1/organisations/{orgId}/accessors/{accessorId}/credential
{
  "credentials": [
    { "credentialType": "card", "format": "32_bit",
      "credentialId": 123456, "userCardType": 1 }
  ]
}

From that point the card behaves like any other credential — bind it to a lock with the same permissions call.

Enabling an access type

Two routes turn a type on. Every field is optional; only what you send is changed.

PATCH/v1/organisations/{orgId}/accessSettings

Organisation level

Enables a type for the whole organisation. A type must be enabled here before any accessor in it can use it.

{ "fingerprint": true, "card": true, "passcodeAccess": true, "qr": false }
PATCH/v1/organisations/{orgId}/accessor/{accessorId}/accessSettings

Accessor level

Enables a type for one user. Note the singular accessor segment here — the permission routes use accessors.

{
  "fingerprintAccess": true,
  "cardAccess": true,
  "passcodeAccess": true,
  "faceAccess": false,
  "qrAccess": false,
  "walletAccess": { "enabled": false, "name": "abhinaya" },
  "dualAuth": false,
  "adminRole": false
}

Responds { "type": "success", "message": "success" }. Any credential it created is read back through the get-credentials API, not from this response.

In your current scope

Godrej uses three types today, and they behave differently enough to be worth stating plainly:

TypeHow manyBound to
Passcodeone credential per lockeach credential to its own access point
Fingerprinta single credentialevery access point the user may open
Card / RFIDone per card you issuethe access points that card should open

Fingerprint is the useful contrast: because permissions are per credential, one fingerprint credential bound to all of a user's locks gives them the same finger on every door, while their passcodes stay different per door. Nothing forces the two types to be managed the same way.

Section 9API reference

Paths are relative to the Permission Management base path (/permissionManagementV3) and authenticated with your integrator token, as with the permission APIs you use today.

POST/v1/organisations/{orgId}/accessors/{accessorId}/credential/create

Create a passcode credential

Issues an additional credential for an accessor that already exists. This is the call that makes a second passcode possible.

Path paramType
orgIdintorganisation
accessorIdintaccessor the credential is created for

Request

{ "credentialType": "passcode" }

Response 200

{ "type": "success",
  "message": { "orgId": 1, "accessorId": 501,
               "credentialType": "passcode", "credentialId": 700000001 } }

Use "passcode" as the credentialType. Store the returned credentialId.

PATCH/v1/organisations/{orgId}/accessors/{accessorId}/credentials/{credentialId}/permissions

Update one credential's doors — credential-centric

Grant or revoke a single credential across a set of doors. This is the call you make during lock onboarding.

Path paramType
orgIdintorganisation
accessorIdintaccessor owning the credential
credentialIdint64the credential being bound

Request

{ "accessPointsToAdd": [101, 102], "accessPointsToRemove": [103] }

Response 200

{ "type": "success", "message": "success" }
  • Either array may be empty; both may be sent in one call.
  • Idempotent. Adding a door the credential already has is a no-op, as is removing one it does not have.
  • The credential type is resolved server-side from credentialId — you do not send it.
  • 400 if the access point does not support the credential type, for example a passcode credential on a lock that has no passcode entry.
PATCH/v1/organisations/{orgId}/accessPoints/{accessPointId}/credential-permissions

Update one door's credentials — door-centric

The same operation seen from the lock: which credentials may open this door. Useful for a "who can open this lock" screen, and for revoking in bulk when a lock is removed.

Request

{
  "credentialsToAdd":    [ { "accessorId": 501, "credentialId": 9001 } ],
  "credentialsToRemove": [ { "accessorId": 502, "credentialId": 9002 } ]
}

Both accessorId and credentialId are required in every pair.

Response 200

{ "type": "success", "message": "success" }

Permission propagation is asynchronous

200 OK on the two PATCH calls means Spintly has accepted and recorded the change, not that the lock has it. The permission is fanned out to the passcode service and reconciled in the background. In practice this is fast, but do not treat the HTTP response as proof the lock is updated.

Section 10SDK changes

The three passcode functions take a new credentialId parameter, inserted after serialNumber. Both iOS and Android are updated.

generateMasterPasscode(String serialNumber, long credentialId, int orgId,
                       long accessorId, String oldPasscode, String newPasscode,
                       KeypadManagerCallback callback)

addUserPasscode(String serialNumber, long credentialId, int orgId,
                long accessorId, String passcode,
                KeypadManagerCallback callback)

updatePasscode(String serialNumber, long credentialId, int orgId,
               long accessorId, String oldPasscode, String newPasscode,
               KeypadManagerCallback callback)

The credentialId you pass must be the credential that holds permission on that lock's access point — granted in flow A step 4 or flow B step 3. Passing a credential with no permission on the lock will not produce a working passcode.

What this means for the app: the lock record must now carry credentialId alongside orgId, accessorId and accessPointId, so the passcode screen can pass all four.

The model change in one line: permission and passcode records move from accessorId → lockId to credentialId → lockId.

Because one accessor now holds several credentials, accessorId alone is no longer a unique key for a passcode. Any table keyed on (accessorId, orgId) for passcode purposes needs credentialId added to the key.

Properties already onboarded

Properties onboarded under the one-lock model keep working unchanged. Their owner has one credential permitted on one lock, which is a valid state under the new model — simply an accessor with one credential. To add a second lock to such a property you need that existing credentialId. If it was not stored at creation time, tell us which organisations are affected and we will supply the values so you can backfill before enabling multi-lock for those users.

Section 12Sequencing rules

These are the ordering constraints that will bite if broken. Each one is a case where the call succeeds only because the previous thing finished.

  1. Organisation, site and network must all be in sync before an accessor or access point is created.
  2. The accessor must be ready (accessor_ready) before any permission is granted.
  3. The access point must be in sync before a credential is bound to it.
  4. A credential must exist before it is bound to a door.
  5. A credential must be bound to the door before its passcode is written to the lock over BLE.

Section 13Binary Veda's calls

Two things in this design are deliberately left to you, because the model supports either answer and the product decision is yours.

How many passcodes a user may hold

There is no server-side cap. You may issue as many passcode credentials per accessor as the product calls for, and impose whatever limit makes sense in the app. If you want a limit, enforce it in your backend before calling credential/create.

Whether a passcode may open more than one lock

Supported, and it needs no extra API. Because you choose which credential goes on which lock, a single passcode opening two locks is just one credential bound to two access points:

PATCH …/accessors/{accessorId}/credentials/700000001/permissions

{ "accessPointsToAdd": [4567, 4568], "accessPointsToRemove": [] }

So the two patterns sit side by side in the same organisation, and you pick per lock:

You wantDo this
A different passcode on each lockcreate a new credential per lock, bind each to its own access point
One passcode across several locksreuse the existing credential and add the other access points to it
Both, for the same usera per-lock credential for each lock, plus one shared credential bound to all of them

The third row is worth calling out: a user can hold a passcode unique to the garage and a master passcode that opens everything, because those are simply two credentials with different bindings. The Passcodes screen in section 8 shows that case.
